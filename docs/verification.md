单台 Windows 11 电脑，16 GB RAM、8 GB NVIDIA 显存。以下来自当时保存的安装记录，未在本次重新操作编辑器。

- Ollama 0.35.1、Continue 2.0.0、VS Code 1.139.1。
- 程序、模型、Continue 目录与插件目录使用示例中的 D 盘路径。
- Ollama 清单能识别 `qwen2.5-coder:1.5b-base`。
- 本地 FIM 请求返回 `return number * number`。
- 当时初次请求约 39.1 秒，单次预热请求约 38 毫秒；两者生成了 5 个 token。
- `ollama ps` 当时显示 100% GPU、2048 上下文。
- 实际在 VS Code 看到灰色建议，并用 Tab 接受 `return number * number`。
- 模型与安装器文件在原安装过程中做过哈希检查。

这些是单机、短示例结果。38 毫秒是一次 API 请求的耗时，不是普遍性能，也不是 VS Code 端到端延迟。

### 本次观察到的两个生成结果

两个请求都使用 `def square(number):` 前缀、2048 上下文、最多 32 个 token、温度 0.2。

第一次请求：

- 总耗时约 3796 毫秒，其中加载约 3633 毫秒。
- 生成 5 个 token，返回 `return number * number`，符合这次示例的意图。
- `/api/ps` 报告加载大小和显存占用均为 1,105,419,304 字节。

第二次请求：

- 总耗时约 360 毫秒，其中加载约 3 毫秒。
- 生成 32 个 token，返回了限制参数为 1–64 的逻辑和未完成的 `return 2**(`。
- 人工检查：这次输出不符合“求数字平方”的意图，且代码不完整。即使服务返回完成标志，也不能算内容验收通过。

样本只有两次，不能据此计算模型准确率或推广性能结论。该结果说明后端健康检查与补全质量检查必须分开。
